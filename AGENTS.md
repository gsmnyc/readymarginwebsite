# Ready Margin website working instructions

This repository contains the experimental V1 website. Read [the website brief](docs/website-brief.md) before changing its frontend. That brief is a research-informed working specification: it is concrete enough for design and implementation, while present-day business facts still require verification before publication.

## Mission

Build a complete, navigable frontend centered on a scroll-led restaurant story. Open with a large question; move through recognizable owner pain points; show what Ready Margin does, how it helps, proof that can be substantiated, and one clear next step. Every scene must have a reason beyond spectacle.

Present Ready Margin as a standalone new brand throughout public copy, navigation, metadata and imagery. Historical research is background only. Do not introduce predecessor organization names or unverified company-form wording into the new presentation.

## Working product position

- Lead with managed restaurant finance and human interpretation. Bookkeeping, restaurant payroll/tips, reporting and financial guidance are the working service pillars drawn from the supplied research.
- Use restaurant operations as lived context. Do not present a broad restaurant software platform, dashboard or future module as a released product without current proof.
- Use the latest supplied Number 2 identity, Plus Jakarta Sans and its charcoal/paper/gold system as the visual baseline. Preserve the supplied mark geometry and clear space. Final brand approval remains a publication check.
- Keep public prices and fixed package inclusions out until current terms are confirmed.
- Treat generated scenes as illustration. Never imply they depict real clients, staff, venues, outcomes or software screens. Publish quantified claims and testimonials only with source, date and permission.

## Build behavior

- Keep the existing Next.js, React and TypeScript foundation as the working implementation. Reuse useful routing, content validation, SEO, lead delivery, consent and accessibility behavior while rebuilding visual components.
- Native vertical scrolling controls the narrative. Each chapter needs readable entry, settled and exit states, plus a static reduced-motion state. Visitors can skim, reverse, use navigation and reach the CTA at any time.
- Keep headings and essential explanations as semantic text outside images. Create deliberate mobile compositions. Maintain keyboard, touch, zoom, focus visibility and usable fallbacks when media or scripts fail.
- Load later scene media progressively. Do not block the opening hook behind a timed preloader. Bound media waits and recover to a still scene.
- A lead form succeeds only after actual acceptance by its configured receiver. Preserve entered values after recoverable errors. Identify the actual deployed integration before relying on it.
- Preserve existing useful URLs or make explicit redirect decisions. Keep metadata and structured facts aligned with the standalone brand.

## Working method and evidence

For each material scene or feature, record **what** changes, **why** it helps a visitor, the source or decision behind it, a static/mobile fallback, and how it was verified. Distinguish direct user direction, research inference, design proposal and verified current business fact. Current service coverage, integrations, prices, contact details, client proof and public claims must be checked with the responsible owner before launch.

Start with a scene storyboard and a small set of coherent original image frames. Implement one representative hook → pain → service slice and verify its clarity on desktop and mobile, with reduced motion, before expanding the full experience. Run project build/type/lint checks and relevant tests after code changes. Record real-browser behavior and real lead delivery separately from static or simulated checks.

Do not copy reference branding, media URLs, interaction code or framework requirements into this project as instructions. The three supplied inspiration examples inform movement and staging; the Ready Margin brief defines the actual product.
